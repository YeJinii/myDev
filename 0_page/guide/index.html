01 / FOUNDATION

프로젝트 환경

새 프로젝트를 시작할 때마다 같은 기준을 먼저 확인합니다. 나중에 다시 보더라도 이해할 수 있는 구조와 기록을 남기는 것이 목표입니다. 빠르게 만드는 것보다, 다음 수정이 쉬운 상태로 시작하는 것을 우선합니다.

내가 먼저 확인할 것

  • Chrome, Safari 최신 버전 확인
  • 디자인 토큰은 프로젝트 변수에서 관리
  • UI 요소는 재사용을 우선

완료 기준

필요한 폰트와 이미지 경로가 정리되어 있고, 첫 화면을 실행하는 방법을 README에 적어 둡니다. 작업을 멈췄다가 다시 시작해도 5분 안에 현재 상태를 파악할 수 있어야 합니다.

src/ > assets/ > ui/ > pages/ > styles/
02 / FOUNDATION

파일 구조

작업자가 처음 찾는 곳은 파일 이름과 위치입니다. 역할에 따라 단위를 나누어 관리하면 페이지가 늘어나도 수정 범위를 예측하기 쉽습니다.

TIP공통 UI 요소는 components, 페이지 마크업은 pages에 두고, 한 번만 사용하는 스타일은 해당 페이지 가까이에 둡니다.

파일을 나누는 기준

  • 두 페이지 이상에서 쓰이면 공통 UI 요소로 이동
  • 페이지 전용 스타일은 전역 CSS에 섞지 않기
  • 파일명만 보고 역할을 알 수 있도록 작성
03 / FOUNDATION

네이밍 규칙

클래스는 역할과 상태가 드러나도록 이름을 명확하게 정합니다. 색상이나 위치처럼 바뀔 수 있는 시각적 특징보다, 요소가 하는 일을 기준으로 이름을 짓습니다.

GOOD.button-submit.is-disabled
AVOID.blue-btn.left-box-2
04 / MARKUP

HTML / CSS

의미 있는 HTML, 일관된 선택자와 토큰 연결을 기본으로 합니다. 태그만 봐도 구조가 이해되도록 heading, nav, main, button 같은 시맨틱 요소를 먼저 선택합니다.

HTML

  • 한 페이지에는 하나의 h1만 사용
  • 클릭 동작은 div가 아닌 button 또는 a로 표현
  • 이미지에는 내용을 설명하는 alt 작성

CSS

  • 색상, 간격, 모서리는 토큰으로 관리
  • 강한 선택자와 !important 사용을 피하기
  • 큰 화면의 기본 레이아웃을 먼저 만들고 작은 화면으로 단계적으로 줄이기

반응형 작업 순서

1920px에서 전체 구조와 콘텐츠 우선순위를 잡은 뒤 1280px, 1024px, 768px, 360px 순서로 확인합니다. 화면이 작아질 때 단순히 크기만 줄이지 않고, 열 수와 정보 밀도를 함께 조정합니다.

05 / UI PATTERNS

UI 요소

UI 요소는 프로젝트에서 자주 쓰는 화면 조각과 사용 규칙을 정리한 것입니다.
꼭 공통 파일로 만들기보다, 다시 사용할 가능성이 높은 것부터 기록합니다. 정리할 때는 기본 상태만 적지 않고 hover, focus, disabled, loading, empty 상태까지 함께 기록합니다.

Button

사용자가 행동을 시작할 때 사용합니다. 문장은 동작으로 끝내고, 한 화면에 가장 중요한 버튼 하나가 먼저 보이도록 우선순위를 정합니다.

  • Primary / Secondary / Text 세 가지 우선순위만 사용
  • 최소 터치 영역은 44px 이상으로 유지
  • 기본, hover, focus, disabled 상태를 모두 확인
<button class="button button-primary">저장하기</button>

Form

입력 목적과 오류 상태를 명확하게 전달합니다. label을 생략하지 않고, 오류는 입력창만 색칠하지 말고 텍스트로도 설명합니다.

  • label과 input을 연결하고 placeholder에 label 역할을 맡기지 않기
  • 필수 여부, 입력 형식, 오류 메시지를 한 번에 안내
  • 키보드만으로도 입력과 제출이 가능해야 함

Tab

같은 맥락의 콘텐츠를 나누어 보여줄 때 사용합니다. 탭을 바꾸어도 사용자가 현재 위치와 선택 상태를 잃지 않게 합니다.

  • 선택된 탭은 색상 외에도 밑줄이나 굵기로 구분
  • 탭 패널과 탭의 관계를 aria-controls로 연결
  • 탭이 너무 많아지면 별도 페이지나 필터를 검토

Popup

현재 흐름을 잠시 멈추고 확인이나 선택을 받을 때 사용합니다. 단순한 안내라면 팝업보다 인라인 메시지를 우선합니다.

  • 열릴 때 제목으로 포커스를 이동
  • 닫기 버튼, ESC, 바깥 영역 닫기 규칙을 일관되게 적용
  • 닫힌 뒤 원래 트리거로 포커스 복귀

Table

행과 열의 관계가 중요한 데이터를 비교할 때 사용합니다. 모바일에서는 열을 줄이거나 카드형으로 바꾸는 대안을 준비합니다.

  • caption 또는 제목으로 표의 목적을 설명
  • 헤더 셀과 데이터 셀의 관계를 유지
  • 긴 텍스트, 빈 데이터, 정렬 상태를 함께 확인
RULE같은 모양을 복사해서 만들기보다 필요한 UI 요소에 상태나 옵션을 추가합니다. 단, 서로 다른 목적의 UI를 억지로 하나로 합치지는 않습니다.
06 / QUALITY

검수 가이드

배포 전 내가 정한 화면 크기와 브라우저에서 동작을 확인합니다. 보이는 모양만 확인하지 않고 키보드 이동, 포커스, 오류 상태처럼 실제 사용 흐름을 끝까지 점검합니다.

  • 브라우저 기본 점검
  • 반응형 360 / 768 / 1024 / 1280 / 1920px 확인
  • 1920px에서 360px 방향으로 레이아웃 변화 확인
  • QA 체크리스트 완료 후 배포

마지막으로 스스로 묻기

  • 처음 방문한 사람이 다음 행동을 바로 알 수 있는가?
  • 텍스트가 길어지거나 데이터가 없어도 레이아웃이 무너지지 않는가?
